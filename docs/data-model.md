# 数据口径

这份文档解释每一个数字是怎么来的。所有参数集中在 [`data/model/prep_time.json`](../data/model/prep_time.json)，
改那里会立刻改变判定结果——这是刻意的，因为"出餐要多久"本来就没有标准答案，应该让用户自己调。

## 1. 时间预算

```
T_budget = deadline_ts − now_ts
```

- `now_ts` 取自 `now-time-info` 返回的**服务端时间**。
- 不用本机时钟：时区设置错误或系统时间漂移会把整个结论算反，而这个项目的全部价值都押在时间上。
- `deadline` 有两种给法：`--deadline 13:00`（绝对时刻）或 `--minutes 40`（相对预算）。
- `T_budget ≤ 0` 时直接判「来不及」，不再推荐任何餐品。

## 2. 步行时间

```
T_walk = max(1, ceil(distance_m × 1.25 ÷ 75))
```

| 项 | 取值 | 理由 |
| --- | --- | --- |
| `distance_m` | `query-nearby-stores` 返回的 `distance`，单位米 | 官方字段，实测 403 / 810 / 1233 等 |
| `1.25` | 绕行系数 | 直线距离必然小于实际步行距离；没有路径规划接口，只能估 |
| `75` | 每分钟米数 | 约 4.5 km/h，普通成年人步行速度 |

- 向上取整：宁可多算一分钟，也不让用户踩着点跑。
- `distance` 缺失或为 0 → 按 400m 估算，并在输出里标注「置信度低」。
- `--walk N` 可由用户直接覆盖，此时输出标注「手动指定」——这是最准的一路。

## 3. 出餐时间（唯一没有接口的量）

```
T_prep = max(2, ceil(base[kind] × busy(t) × (1 + 0.15 × (n − 1))))
```

`base`（分钟）：

| 品类 | 基值 | 判定依据 |
| --- | --- | --- |
| `combo` 套餐 | 5.5 | `query-meal-detail` 有 `rounds` 分组 |
| `burger` 汉堡单品 | 4.0 | 分类含「堡」 |
| `snack` 小食 | 3.0 | 薯条 / 鸡块 / 鸡翅 / 玉米 |
| `drink` 饮料 | 2.0 | 可乐 / 雪碧 / 咖啡 / 茶 |
| `dessert` 冰品 | 2.0 | 冰淇淋 / 新地 / 麦旋风 / 派 |

`busy`（时段系数）：11:30–13:00 ×1.4，17:30–19:00 ×1.3，其余 ×1.0。

`n` = 这一单包含的单品件数（从 `rounds[].choices` 里 `quantity > 0` 的项求和）。
三件套会让出餐变慢，但不是线性变慢，所以用 `1 + 0.15×(n−1)` 而不是 `×n`。

> **这是先验模型，不是门店实时数据。** 没有任何官方接口返回"当前排队几分钟"。
> 所有输出都把这句话显式打出来，不假装自己知道。

## 4. 用餐时间

```
T_eat = clamp(round(kcal ÷ 60), 6, 20)
```

- 约 60 kcal/分钟，对应"赶时间、专心吃"的节奏。
- 下限 6 分钟：再少就不是吃饭了。
- 上限 20 分钟：防止 1200 kcal 的套餐算出"要吃半小时"从而把结论带偏。
- 热量未知 → 该项不进入推荐（见 §5）。

## 5. 热量

只认 `list-nutrition-foods` 的 `energyKcal`，按 `productName` 匹配套餐内的每个单品，然后求和。

匹配顺序：
1. 精确匹配；
2. 去掉括号后缀再精确匹配（`巨无霸（经典）` → `巨无霸`）；
3. 双向包含匹配，取最长命中；
4. 都没有 → 记一次 `missing`。

```
kcal_lo = Σ(命中项 kcal × 数量)
kcal_hi = kcal_lo + 90 × missing      # 90 kcal 是"一个未知小件"的经验上界
kcal_mid = (kcal_lo + kcal_hi) ÷ 2    # 仅在 missing > 0 时使用
coverage = (总件数 − missing) / 总件数
```

**硬规则：`kcal_lo == 0` 的候选一律不推荐**，并在 notes 里说明"热量在官方营养表里查不到，已排除（不给假数字）"。

实测例子：`鸡肉堡单品精选` 的主体是 `双层脆鸡堡`，这个名字不在 160 条营养表里，
所以它的热量是"未知"而不是"0 大卡"——把未知当 0 会让它错误地成为"最健康的选择"。

## 6. 可行性判定

```
wait    = max(T_walk, T_prep)          # 步行与出餐并行
need    = wait + T_eat + T_walk + buffer
slack   = T_budget − need

slack ≥ 3   → 来得及
0 ≤ slack < 3 → 卡线
slack < 0   → 来不及
```

`buffer` 默认 5 分钟，扣给找店、取餐柜、等电梯、过马路。用 `--buffer` 可调。

**为什么取 `max` 而不是相加**：下单之后你在走向门店，后厨同时在做。两者是并行事件。
按加法算会系统性高估 5–10 分钟，足以把"来得及"误判成"来不及"。

完整算例（以「麦乐鸡经典中套餐」为例，12:20 / 40 分钟）：

```
T_walk = ceil(403 × 1.25 ÷ 75) = ceil(6.72) = 7
T_prep = ceil(5.5 × 1.4 × 1.3) = ceil(10.01) = 11     # 午高峰的三件套
wait   = max(7, 11) = 11
T_eat  = round(649 ÷ 60) = 11
need   = 11 + 11 + 7 + 5 = 34
slack  = 40 − 34 = 6  → 来得及
最晚下单 = 13:00 − 34 分钟 = 12:26
```

## 7. 价格

```
price_yuan = calculate-price.data.price ÷ 100
```

- 单位是**分**，`3750` → `¥37.50`。
- 只用这个接口的应付总额（已含门店价、套餐价、优惠），**绝不用菜单单价 × 数量自算**。
- 单项小计优先取 `productList[].subtotal`；缺失时按总额均摊，并在 notes 里标注"仅供参考"。

## 8. 排序目标（三场景不同）

| 场景 | 过滤 | 排序键 |
| --- | --- | --- |
| 1 还来不来得及 | 只留正餐（套餐/汉堡，或 ≥350 kcal） | 余量降序 → 总耗时升序 |
| 2 只剩几分钟 | 不过滤（小食也算合理选择） | 出餐升序 → 用餐升序 → 余量降序 |
| 3 三重约束 | 正餐 + 热量上限 + 预算上限 | 价格升序 → 热量升序 → 余量降序 |

"正餐"的判定用 `kind in (combo, burger) or kcal_mid ≥ 350`，而不是单纯卡热量——
289 kcal 的中薯条能过热量线，但它不是一顿饭。

## 9. 无解时的行为

可行集为空时不返回空结果，而是：

1. 在"未通过筛选"的候选里找**违反程度最小**的一个（各约束按相对超出比例加权）；
2. 输出「最接近的一单是 X：热量放到 649 kcal 就能吃上」这类**可执行**的建议；
3. 如果连"违反约束"的都没有（即满足全部约束的只有零嘴），明确说"只有零嘴能满足，没有正餐选项"。

## 10. 边界情况

| 情况 | 处理 |
| --- | --- |
| 截止时刻已过（预算 ≤ 0） | 判「来不及」，不进推荐，不显示最晚下单时刻 |
| 门店已打烊 / 营业时间跨零点 | 按 `businessStartTime`/`businessEndTime` 区间判断，`end < start` 视为跨天 |
| 距离缺失 | 400m 兜底 + 「置信度低」标注 + 允许 `--walk` 覆盖 |
| 营养表未覆盖某单品 | 见 §5，给区间与覆盖率，不填 0 |
| 套餐内某轮有多个选项但都未选中 | 只用 `quantity > 0` 的项；若无任何选中项则回退到套餐名本身 |
| 热量上限低于所有正餐 | 输出"最接近 + 差多少卡"（见 §9） |
| 价格接口未返回单项小计 | 按总额均摊 + 标注 |
| 429 限流 | 指数退避 3 次（1/2/4 秒），仍失败则报错，不静默降级到旧数据 |
| 401 | 不重试，直接提示检查 `MCD_MCP_TOKEN` |
