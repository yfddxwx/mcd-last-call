# 时间与热量模型

全部参数在 `data/model/prep_time.json`，改那里会立刻改变判定结果。

## 1. 时间预算

```
T_budget = deadline − now
```

- `now` 取自 `now-time-info` 的 `data.datetime`，**不用本机时钟**——时区或漂移会把结论算反。
- `T_budget ≤ 0` → 直接判"来不及"，不给推荐。

## 2. 步行

```
T_walk = max(1, ceil(distance_m × 1.25 ÷ 75))
```

| 项 | 值 | 说明 |
| --- | --- | --- |
| `distance_m` | 门店字段 `distance` | 单位是**米**，接口直接给 |
| 1.25 | 绕行系数 | 直线距离小于实际步行距离；无路径规划接口 |
| 75 | 米/分钟 | ≈ 4.5 km/h |

距离缺失 → 按 400m 估并标注"置信度低"；用户给了分钟数就用用户的。

## 3. 出餐（没有官方接口，只能结构估算）

```
T_prep = max(2, ceil(base[kind] × busy(t) × (1 + 0.15 × (n − 1))))
```

| kind | base | 判定依据 |
| --- | --- | --- |
| `combo` | 5.5 | 详情有 `rounds` 分组 |
| `burger` | 4.0 | 分类/名称含"堡" |
| `snack` | 3.0 | 薯条 / 鸡块 / 鸡翅 / 玉米 |
| `drink` | 2.0 | 可乐 / 雪碧 / 咖啡 / 茶 |
| `dessert` | 2.0 | 冰淇淋 / 新地 / 麦旋风 / 派 |

`busy(t)`：11:30–13:00 ×1.4，17:30–19:00 ×1.3，其余 ×1.0。
`n`：这一单包含几件（`rounds` 里 `quantity > 0` 的项数）。

**必须在输出里说明这是估算**，不要让用户以为是实时排队时间。

## 4. 用餐

```
T_eat = clamp(round(kcal ÷ 60), 6, 20)
```

60 kcal/分钟 ≈ 赶时间专心吃的节奏；下限 6 分钟，上限 20 分钟（防止 1200 kcal 的套餐算出"吃半小时"）。

## 5. 可行性

```
wait   = max(T_walk, T_prep)     ← 并行，绝不是相加
need   = wait + T_eat + T_walk + buffer
slack  = T_budget − need

slack ≥ 3      → 来得及
0 ≤ slack < 3  → 卡线
slack < 0      → 来不及
```

`buffer` 默认 5 分钟（找店、取餐柜、等电梯）。

## 6. 最晚下单时刻

```
LOT = deadline − buffer − max(T_walk, T_prep) − T_eat − T_walk
```

推导：若在 `t` 下单，则 `t + max(walk, prep) + eat + walk ≤ deadline − buffer`。
解出 `t` 的上界即 LOT。`prep < walk` 时该式偏保守，宁可早说一分钟。

## 7. 算例（12:20 / 截止 13:00 / 403m / 三件套 394 kcal）

```
T_walk = ceil(403 × 1.25 ÷ 75) = 7
T_prep = ceil(5.5 × 1.4 × 1.3) = 11        # 午高峰三件套
wait   = max(7, 11) = 11
T_eat  = clamp(round(394 ÷ 60)) = 7
need   = 11 + 7 + 7 + 5 = 30
slack  = 40 − 30 = 10  → 来得及
LOT    = 13:00 − 30 分钟 = 12:30
```

若按"相加"的错法：`7 + 11 + 7 + 7 + 5 = 37`，LOT 会变成 12:23——**少给用户 7 分钟**。

## 8. 热量

```
kcal_lo = Σ(命中项 kcal × 数量)
kcal_hi = kcal_lo + 90 × 缺失项数
```

匹配顺序：精确 → 去括号 → **归一化后精确**（去掉空格/连字符/引号，
让 `麦辣鸡翅2块` 对上 `麦辣鸡翅-2块`）→ 归一化后包含。

硬规则：`kcal_lo == 0` 的候选**不推荐**，并说明"热量在官方营养表里查不到"。
把未知当 0 会让"查不到热量"的餐品变成"最健康的选择"。

## 9. 价格

```
price_yuan = calculate-price.data.price ÷ 100
```

单位是**分**。只用这个接口的应付总额，绝不用"菜单单价 × 数量"自算——
门店价、套餐价、券门槛都会让自算结果偏掉。
单项小计优先取 `productList[].subtotal`，缺失时按总额均摊并标注。

## 10. 三种排序目标

| scenario | 过滤 | 排序 |
| --- | --- | --- |
| 1 | 只留正餐（`combo`/`burger` 或 ≥350 kcal） | 余量降序 → 总耗时升序 |
| 2 | 不过滤，小食也算合理 | 出餐升序 → 用餐升序 → 余量降序 |
| 3 | 正餐 + 热量上限 + 预算上限 | 价格升序 → 热量升序 → 余量降序 |

"正餐"用品类判定，不要只看热量——289 kcal 的中薯条能过热量线，但它不是一顿饭。

## 11. 边界

| 情况 | 处理 |
| --- | --- |
| 截止已过 | 判"来不及"，不显示 LOT |
| 门店打烊 / 跨零点 | 用营业时段判断，`end < start` 视为跨天 |
| 距离缺失 | 400m 兜底 + 标注置信度低 |
| 热量缺失 | 给区间 + 说明；全未命中则不推荐 |
| 可行集为空 | 找"违反程度最小"的一单，说明该放宽哪个条件到多少 |
| 商品需资格（学生/亲子）或非餐品（周边） | 直接排除，不要推荐给所有人 |
